# EXECUTION_PLAN.md — SwiftBruja Local Agentic CLI

> Generated by `/mission-supervisor breakdown REQUIREMENTS.md`. This plan decomposes the
> POC laid out in [REQUIREMENTS.md](REQUIREMENTS.md) into work units and sorties.
>
> **Architectural note (read OQ-1 first).** REQUIREMENTS.md R1/R4 propose a hand-rolled
> `AgentBackend` / `AgentEvent` abstraction with two separate tool adapters. The project's
> **locked, superseding direction** (the `project-bruja-agentic-cli-direction` decision of
> 2026-06-19, already reflected in `Package.swift`'s macOS-27 / tools-6.4 retarget) is to
> conform to Apple's `FoundationModels` `LanguageModel` + `LanguageModelExecutor` seam and
> write ONE `MLXLanguageModelExecutor`, with tools defined ONCE as `@Generable` FM `Tool`s.
> This plan is decomposed against that superseding direction. **This was confirmed in `refine`
> Pass 1 (2026-06-19): build against the `LanguageModelExecutor` seam.** See the
> [Resolved Decisions](#resolved-decisions) section for the full record.

## Terminology

> **Mission** — A definable, testable scope of work. Defines scope, acceptance criteria, and dependency structure.

> **Sortie** — An atomic, testable unit of work executed by a single autonomous AI agent in one dispatch. One aircraft, one mission, one return.

> **Work Unit** — A grouping of sorties (package, component, phase).

> `make build`/`make test`; if the existing Sources still `import` removed/nonexistent modules,
> S1 fails on contact for reasons unrelated to its own work. This sortie is the critical-path root.

### Sortie 1: Unified tool foundation + `read_file` tool

**Entry criteria**:
- [ ] Sortie 0 exit criteria met (package compiles clean against the pared-back deps; no dead imports)
- [ ] Architecture direction: build against Apple's `LanguageModelExecutor` seam (resolved 2026-06-19; see Resolved Decisions)

**Tasks**:

2. Implement `ReadFileTool` conforming to `FoundationModels.Tool` with a `@Generable` `Arguments` struct (`path: String`) in `Sources/SwiftBruja/Agent/Tools/ReadFileTool.swift`. `call(arguments:)` reads the file and returns a compact result string.
3. Establish the tool-registry shape that yields the single `[any Tool]` array consumed by both backends (R4.1) in `Sources/SwiftBruja/Agent/Tools/ToolRegistry.swift`.

**Exit criteria**:

### Sortie 2: Minimal `MLXLanguageModelExecutor` — one tool round-trips end-to-end

**Entry criteria**:
- [ ] Sortie 1 exit criteria met (`ReadFileTool` + registry compile and unit-test green)
- [ ] Tokenizer source resolved: drive generation through `MLXLMCommon`'s `TokenizerLoader` (already a declared product; `MLXLMTokenizers` is NOT a real product in mlx-swift-lm 3.31.3); see corrected Resolved Decisions OQ-2

**Tasks**:
1. Implement a minimal `MLXLanguageModelExecutor` conforming to `FoundationModels.LanguageModelExecutor` (`@available(macOS 27.0, *)`) in `Sources/SwiftBruja/Agent/MLXLanguageModelExecutor.swift`, driving `mlx-swift-lm` generation via the existing `ModelContainer` path (reuse `BrujaQuery.resolveModel` in `Sources/SwiftBruja/Core/BrujaQuery.swift`). The conformance surface is `respond(to: LanguageModelExecutorGenerationRequest, model:, streamingInto: LanguageModelExecutorGenerationChannel)`, `init(configuration:)`, and (optionally) `prewarm(model:transcript:)` — **API-confirmed against Apple docs (refine supplemental pass)**. Tokenize/detokenize via `MLXLMCommon`'s `Tokenizer`/`TokenizerLoader` seam — **but note both are protocols only; you must implement a concrete `TokenizerLoader`** that reads `tokenizer.json`/config from the resolved model directory and returns `any Tokenizer`. Do NOT depend on `swift-tokenizers` directly. **Prerequisite source fix (done in S0)**: `BrujaModelManager.swift:5` does `import MLXLMTokenizers`, which is **not a product in mlx-swift-lm 3.31.3** (verified: 3.x exposes `MLXLLM`/`MLXVLM`/`MLXLMCommon`/`MLXEmbedders`/`MLXHuggingFace` only) and will not compile — remove it. **No manifest product addition is required or possible** (see corrected OQ-2).
2. Define an `MLXLanguageModel` conforming to `FoundationModels.LanguageModel` whose associated `Executor` is `MLXLanguageModelExecutor` and whose `Configuration` carries the resolved MLX `ModelContainer`/model id. The framework instantiates the executor from this model's `Configuration` via `init(configuration:)` — **you pass the model to the session, never the executor** (API-confirmed).
3. Parse tool-call tokens from the MLX generation stream and emit the executor's channel events (`.response` text + `.toolCalls`) — the one place we control, per REQUIREMENTS §3a. Confirmed event surface: `LanguageModelExecutorGenerationChannel.Event` with `.response`, `.toolCalls`, `.reasoning`.
4. Wire a demonstration path: construct `LanguageModelSession(model: MLXLanguageModel(...), tools: [ReadFileTool()], instructions: ...)` (real init: `init(model:tools:instructions:)`) and run a prompt that forces a `read_file` call against the small fixture model (`mlx-community/Qwen2.5-0.5B-Instruct-4bit`, per Makefile `SMALL_FIXTURE_MODEL`).
5. Add an inference integration test in `Tests/BrujaIntegrationTests/AgentSeamSpikeTest.swift` that asserts the session invokes `read_file` and the file's content appears in the final transcript/response.

**Exit criteria**:
- [ ] `make build` succeeds; `MLXLanguageModelExecutor.swift` exists and conforms to `LanguageModelExecutor`, and `MLXLanguageModel` conforms to `LanguageModel` with `Executor == MLXLanguageModelExecutor`.
- [ ] `make test` (or the integration target) runs `AgentSeamSpikeTest` and it passes against the fixture model: a `read_file` tool call is observed and its result round-trips back into the model's continuation.
- [ ] No direct dependency on the removed `swift-tokenizers` package is reintroduced in `Package.swift`; the stale `import MLXLMTokenizers` is gone from `BrujaModelManager.swift` and tokenizer loading routes through `MLXLMCommon` (grep: no `MLXLMTokenizers` remains under `Sources/`).

### Sortie 4: Working-directory confinement guard (R6.1–R6.4)

**Entry criteria**:
- [ ] Sortie 3 exit criteria met (full tool suite exists)

**Tasks**:
1. Implement `PathGuard` in `Sources/SwiftBruja/Agent/PathGuard.swift`: canonicalize/resolve a candidate path (handling `..`, absolute paths, and symlinks), classify it as inside-cwd-subtree or escaping, and deny-by-default when it cannot be resolved safely (R6.2).
2. Integrate `PathGuard` into every filesystem tool (`read_file`/`write_file`/`edit_file`/`list_dir`/`grep`/`glob`): in-cwd operations proceed without confirmation (R6.1); escapes raise an "escape requested" outcome routed to the consent flow (the consent UI itself lands in Sortie 6/7).
3. Add a best-effort outside-path detection for `run_shell` command strings (R6.2), and the auditable echo of every command/edit performed (R6.3).
4. Document the best-effort confinement limit for `run_shell` in code comments (R6.4).
5. Add unit tests in `Tests/SwiftBrujaTests/Agent/PathGuardTests.swift`: in-cwd path allowed; `..`-escape, absolute-escape, and symlink-escape each flagged as escaping; unresolvable path denied.

**Exit criteria**:
- [ ] `make build` succeeds; `PathGuard.swift` exists.
- [ ] `make test` runs `PathGuardTests` and it passes for all five cases (in-cwd allow; `..`/absolute/symlink escape; unresolvable deny).
- [ ] Every filesystem tool calls `PathGuard` before touching disk (asserted by a test that a constructed escaping path is rejected at the tool boundary).

## Parallelism Structure (refine Pass 4)

**Critical path**: S0 → S1 → S2 → S3 → S4 → S6 → S7 → S8 → S9 → S11 → S12 (length: **11 sorties**).

**Honest constraint — this plan is build-serialized.** Nearly every sortie's exit criteria require `make build`/`make test`, and **only the supervising agent builds**. That caps *effective* parallelism low: sub-agents can draft source/tests for an independent sortie, but the verifying build that closes each sortie's exit gate must serialize through the supervisor.

**Parallelizable clusters** (drafting only; verification serializes):
- **After S3**: S4 (`PathGuard.swift` + tool integration) and S5 (`MLXLanguageModelExecutor` hardening + `BrujaError`) touch disjoint files — a sub-agent may draft one while the supervisor builds the other.
- **Layer 4**: S10 (serve, fully fenced per WU5) and S11 (mock harness) share no files once their deps are met.

**Agent allocation**: 1 supervising agent + up to 1 effective sub-agent (drafting). Build/compile/test steps — i.e. **every sortie here** — are **supervising-agent-only**. Sub-agent value in this mission is marginal; the dependency chain is the real bottleneck, not agent count.

**Missed opportunities**: none material. The critical path is intrinsic (each layer genuinely depends on the prior), so adding agents would not shorten wall-clock.
